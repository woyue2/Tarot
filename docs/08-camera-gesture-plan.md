# 摄像头魔法手势模式规划

> 本文对应 `project_init.md` 原则 #12 与《产品体验与选牌交互》§8 的可选实验：摄像头魔法手势。该功能**明确不进入第一版 MVP**，仅作为后续可关闭、可撤销、保留鼠标/键盘/触摸操作的沉浸模式推进。

## 1. 背景与定位

当前选牌以鼠标点击、键盘导航和触摸点选为主。摄像头手势模式不是替代输入，而是一个可选的「仪式化」增强层，适合想要更沉浸抽牌体验的用户。

关键约束（来自现有产品决策）：

- 默认关闭，应用启动时不自动开启。
- 必须保留鼠标、键盘、触摸操作的完整可用性。
- 识别结果先变成可见预览，不能直接提交。
- 最终确认需要持续手势 + 倒计时 + 撤销机会。
- 摄像头帧只在本机内存处理，不写入数据库，不保存照片/视频。
- 不允许手势绕过「五张牌已选满」的状态校验。

## 2. 目标与非目标

### 目标

- 在「选牌阶段」提供一个可开关的摄像头手势模式。
- 支持：挥手浏览、捏合选牌、张开手掌取消、保持确认手势倒计时确认。
- 所有手势动作最终复用现有 `selectedIndexes` / `toggleCard` / `confirmSelection` 状态机。
- 失败、光线不足或用户手动关闭时，自动回退到常规输入。

### 非目标

- 不替代任何现有输入方式。
- 不进入第一版 MVP 发布范围。
- 不做复杂自定义手势训练或多人手势识别。
- 不在主流程中强制要求摄像头权限。
- **不在移动端实施**：摄像头手势模式为桌面端独占的实验功能，移动端选牌沿用触摸点选，不做手势适配。

## 3. 手势词表

| 手势 | 含义 | 触发方式 | 反馈 |
|---|---|---|---|
| 手掌左右移动（挥手） | 浏览牌组 | 手掌中心横向位移累计超过阈值 | 牌列跟随滚动，高亮当前目标牌 |
| 拇指与食指捏合 | 选择当前高亮牌 | 捏合动作完成并持续约 300ms | 预览「选择第 N 张」；释放后执行 |
| 五指张开手掌 | 取消当前高亮牌的选择 | 手掌张开并持续约 300ms | 预览「取消选择」；释放后执行 |
| 保持确认手势 2 秒 | 进入确认倒计时 | 手势稳定保持 2 秒 | 倒计时环 + 「即将确认」提示；倒计时内可撤销 |
| 双手交叉/放下 | 暂停识别 | 双手离开画面或做暂停手势 | 识别暂停，显示「手势已暂停」|

确认手势建议：握拳或「OK」手势，与捏合区分明显；也可复用张开手掌但要求另一只手同时出现，避免误触。

## 4. 技术选型

### 4.1 手势识别方案

方案：**MediaPipe Hands（本地 21 个手部关键点）+ 项目内启发式规则**

- 在 Electron Renderer 中通过 `@mediapipe/tasks-vision` 或 `@mediapipe/hands` 运行。
- 不调用云端 API，符合「本地优先」隐私模型。
- 对挥手/捏合/张开/保持这几类简单手势，基于关键点距离和角度做启发式判断足够，无需训练模型。

备选方案：

- **MediaPipe Gesture Recognizer**：内置一些预定义手势，但对自定义「确认」手势支持有限。
- **Handtrack.js**：轻量但精度不足，不推荐用于正式功能。
- **TensorFlow.js Handpose**：已停止维护，MediaPipe 更活跃。

推荐采用 MediaPipe Hands + 自研启发式，原因：

1. 完全离线，模型可随应用分发。
2. 控制力强，可以精确定义每个手势的判定阈值。
3. 与现有 TypeScript/React 技术栈融合成本低。

### 4.2 视频流

- 使用 `navigator.mediaDevices.getUserMedia` 获取摄像头画面。
- Electron 主进程需要在 `session.setPermissionRequestHandler` 中处理摄像头权限请求，并提示用户。
- 视频分辨率建议 320×240 或 480×360，帧率 15 FPS，降低 CPU/GPU 占用。

```text
┌─────────────────────────────────────────────────────────────┐
│                     选牌界面 (SelectView)                     │
│  ┌───────────────────────────────────────────────────────┐  │
│  │              MagicGestureLayer（手势层）                │
│  │  ┌─────────────┐  ┌──────────────┐  ┌──────────────┐  │  │
│  │  │  CameraView │  │ GestureEngine │  │ GestureHUD   │  │  │
│  │  │  摄像头预览  │  │  手势识别引擎  │  │ 状态/倒计时  │  │  │
│  │  └─────────────┘  └──────────────┘  └──────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
│                          │                                   │
│          调用现有回调：onToggle / onConfirm                   │
│          操作 DOM：deck-scroller scrollLeft                   │
└─────────────────────────────────────────────────────────────┘
```

### 5.1 新增模块建议

在 `apps/desktop/src/renderer/src/` 下新建：

```
gesture/
  camera-permission.ts    # 权限请求与状态管理
  gesture-engine.ts       # MediaPipe 初始化与关键点流
  gesture-classifier.ts   # 挥手/捏合/张开/保持判定
  gesture-state-machine.ts# 手势 → 动作的状态机
  MagicGestureLayer.tsx   # UI 层（预览、HUD、开关）
  useMagicGesture.ts      # React Hook 封装
```

### 5.2 与核心逻辑的边界

- `gesture-engine` 只输出**语义事件**：`wave-left`、`wave-right`、`pinch`、`open-palm`、`hold-confirm`。
- `gesture-state-machine` 决定事件是否转化为动作，处理防抖、预览、倒计时。
- `MagicGestureLayer` 通过**现有 props** 影响界面：调用 `onToggle(index)` 选牌，调用 `scrollTo` 滚动牌列，调用 `onConfirm()` 确认。
- 绝不直接修改 `selectedIndexes`、洗牌种子或确认状态，保证核心状态机唯一。

## 6. 状态机

```text
            ┌─────────────┐
            │    off      │  用户未开启手势模式
            └──────┬──────┘
                   │ 用户点击「开启魔法手势」
                   ▼
            ┌─────────────┐
            │  requesting │  请求摄像头权限
            │  permission │
            └──────┬──────┘
                   │
         ┌─────────┴─────────┐
         │ denied / error     │ granted
         ▼                    ▼
   ┌────────────┐       ┌─────────────┐
   │  fallback  │       │   idle      │  等待识别到手势
   │ 回退到鼠标  │       └──────┬──────┘
   └────────────┘              │ 检测到手势
                               ▼
                        ┌─────────────┐
                        │  preview    │  显示「如果保持此手势，将执行 X」
                        └──────┬──────┘
                               │ 手势释放/持续
                  ┌────────────┼────────────┐
                  ▼            ▼            ▼
            ┌────────┐   ┌──────────┐  ┌──────────┐
            │ action │   │ countdown│  │  cancel  │
            │ 执行   │   │ 确认倒计时│  │ 撤销/暂停│
            └────────┘   └────┬─────┘  └──────────┘
                              │ 倒计时结束
                              ▼
                        ┌─────────────┐
                        │   confirm   │
                        │ 调用 onConfirm│
                        └─────────────┘
```

关键规则：

- 从 `preview` 到 `action` 需要手势**稳定**超过阈值时间（如 300ms），避免抖动。
- `countdown` 阶段用户改变手势或移开手 → 立即取消。
- 任何状态下检测到光线过暗 / 摄像头断开 → 进入 `fallback`，提示用户并关闭手势层。

## 7. 与现有选牌逻辑的集成

### 7.1 桌面端集成

当前 `App.tsx` 中的相关状态和回调：

- `selectedIndexes: number[]`
- `toggleCard(index: number)`
- `clearSelection()`
- `reshuffle()`
- `confirmSelection()`
- `shuffling`, `busy`
- `.deck-scroller` 容器，内部是 78 个 `.deck-card` 按钮

手势层需要：

1. `ref` 指向 `.deck-scroller`，通过 `scrollTo({ left, behavior: 'smooth' })` 实现挥手浏览。
2. 根据滚动位置计算「当前高亮牌」的 `index`（取视口中心最近的 `.deck-card`）。
3. 捏合时调用 `toggleCard(highlightedIndex)`；张开手掌时同样调用 `toggleCard(highlightedIndex)` 以取消。
4. 保持确认手势倒计时结束后，仅在 `selectedCount === 5` 时调用 `confirmSelection()`；否则提示「还需选择 X 张」。
5. 当 `shuffling || busy` 时，手势层进入暂停状态，不响应任何手势。

## 8. 隐私、权限与安全约束

1. **权限请求**：首次开启时弹窗说明用途，明确请求摄像头权限；拒绝后不再自动弹出，入口显示「需要摄像头权限」。
2. **不保存任何画面**：每一帧分析完即丢弃；不写入磁盘、数据库或上传网络。
3. **可立即关闭**：手势层右上角常驻「关闭摄像头」按钮，点击后立即停止视频流并释放摄像头。
4. **系统级指示**：遵循 Windows 摄像头指示灯机制，用户能直观知道摄像头正在工作。
5. **不绕过状态校验**：手势层只能调用已有的 `onToggle` / `onConfirm`，这些回调内部已经包含「最多 5 张」「满 5 张才能确认」的校验。
6. **儿童与误触**：手势模式默认关闭，且开启流程包含明确确认；倒计时和撤销机制防止误操作。

## 9. UI/UX 设计

### 9.1 入口

在选牌页面底部操作栏左侧增加一个切换按钮：

```text
[✋ 魔法手势]  重新洗牌  清空  确认揭牌
```

- 未开启时：幽灵按钮样式。
- 开启后：按钮变为高亮，旁边显示摄像头工作状态指示点。

### 9.2 手势层界面

- **摄像头预览**：右下角小圆角窗口（约 160×120），镜像显示，方便用户看到自己的手。
- **手势提示**：预览窗口下方显示当前识别到的手势图标 + 文字，例如「👋 向左挥手 · 浏览牌组」。
- **目标高亮**：牌列中被手势指向的牌增加金色描边和轻微放大，让用户知道捏合/张开会影响哪张牌。
- **确认倒计时**：屏幕中央显示 2 秒环形倒计时，文字「保持手势以确认」；倒计时期间用户移开手即取消。
- **撤销 Toast**：手势执行选牌/取消后，右下角弹出 3 秒 Toast，带「撤销」按钮。

### 9.3 失败与降级

- 摄像头不可用 / 权限被拒：按钮置灰，Tooltip 显示原因。
- 光线过暗 / 长时间未检测到手：提示「光线不足，已暂停手势识别」，并提供「继续使用鼠标」按钮。
- 用户开启系统「减少动态效果」时：关闭手势预览动画，使用即时反馈。

## 10. 性能与降级

### 10.1 性能目标

- 手势识别 CPU 占用在主流 Windows 笔记本上控制在单核 15% 以下。
- 抽牌界面帧率保持 30 FPS 以上。

### 10.2 性能手段

- 视频流分辨率 ≤ 480×360。
- 识别帧率限制到 15 FPS。
- MediaPipe 模型复杂度选择 `lite`。
- 使用 `requestAnimationFrame` 节流 UI 更新。
- 若检测到连续掉帧，自动降低识别帧率或暂停识别。

### 10.3 多线程

- 初期可在 Renderer 主线程运行，简化调试。
- 稳定后迁移到 WebWorker，利用 `OffscreenCanvas` 处理视频帧，避免阻塞 React 渲染。

## 11. 实施阶段

建议分为 5 个阶段（Phase 0–4）推进，每个阶段可独立验证，不阻塞主分支发布。

### Phase 0：技术预研（1–2 天）

- 在独立原型页面（如 `prototype-camera-gesture.html`）接入 MediaPipe Hands。
- 验证 Windows  Electron 中 `getUserMedia` 的权限流程。
- 输出手势判定阈值的基准数据（不同光线、距离下的误检率）。

### Phase 1：引擎与分类器（2–3 天）

- 实现 `gesture-engine.ts`（MediaPipe 封装）。
- 实现 `gesture-classifier.ts`（挥手/捏合/张开/保持判定）。
- 实现 `gesture-state-machine.ts`（防抖、预览、倒计时逻辑）。
- 单元测试：给定关键点序列，验证输出的事件序列。

### Phase 2：手势层 UI（2–3 天）

- 实现 `MagicGestureLayer.tsx`（预览窗口、HUD、倒计时、Toast）。
- 实现入口开关和权限请求 UI。
- 在桌面端 `SelectView` 中集成，仅预览模式（手势识别显示但不执行动作）。

### Phase 3：动作集成与回退（2–3 天）

- 将手势事件绑定到 `onToggle`、`scrollTo`、`onConfirm`。
- 实现失败/权限被拒/光线不足回退。
- 加入手势操作的撤销 Toast。
- 确保 `prefers-reduced-motion` 下无过度动画。

### Phase 4：验收与优化（2–3 天）

- 邀请 3–5 位用户做可用性测试，收集误触率和手势舒适度。
- 根据反馈调整阈值、确认手势、倒计时时长。
- 补充文档和隐私说明。

总估算：**9–14 天**（1 名前端全栈），不含设计走查。

## 12. 风险与验收标准

### 主要风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| MediaPipe 模型体积大 | 安装包增大 | 按需下载模型，或打包时压缩；首次使用时下载并缓存 |
| 误触率高 | 用户体验差 | 增加稳定时间、倒计时、撤销；允许随时关闭 |
| 性能占用高 | 低端机卡顿 | 降低分辨率/帧率；提供自动暂停；持续跑性能基线 |
| 隐私敏感 | 用户抵触 | 明确告知、默认关闭、不保存画面、即时关闭入口 |

### 验收标准

- [ ] 手势模式默认关闭，开启/关闭切换流畅。
- [ ] 挥手浏览延迟 < 200ms，目标牌高亮准确。
- [ ] 捏合选牌/张开取消的误操作率 < 5%（内部测试 30 次）。
- [ ] 确认倒计时可撤销，满 5 张前不能确认。
- [ ] 摄像头断开、权限被拒、光线过暗均有清晰回退提示。
- [ ] 关闭手势模式后摄像头指示灯熄灭，视频流完全释放。
- [ ] 鼠标、键盘、触摸操作在手势模式开启时依然 100% 可用。

## 13. 前置依赖

本规划假设以下前提已满足或同步推进：

1. **选牌核心状态机稳定**：`selectedIndexes`、`toggleCard`、`confirmSelection` 等接口不再大幅改动。
2. **输入层可用**：桌面端鼠标点击、键盘导航能正常工作。手势层的挥手浏览操作 `.deck-scroller` 的 `scrollLeft`，需确保不破坏现有 `onClick` 选牌路径。
3. **Astryx 主题支持浮层/Toast/倒计时组件**：若现有组件库缺少，需要补充或手写。
