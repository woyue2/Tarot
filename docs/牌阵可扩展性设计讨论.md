# 牌阵（Spread）可扩展性设计讨论

> 底稿用途：记录 0Tarot 项目当前牌阵实现现状、docs 中的牌阵大全盘点，以及"支持多牌阵 + 牌数不一致"的适配方案与开放决策点。
> 讨论状态：待定稿，下文为分析 + 提案，尚未落地代码。

---

## 1. 背景与目标

用户希望项目**支持不同的牌阵，且牌的数量可以不一致**，并确认是否已有可扩展接口。

初步结论：当前项目在"思想层"留下了 `spread` 字段，但"实现层"完全没留接口——牌数 `5` 被写死在运行时守卫、schema、评分公式、模型提示词、两端 UI 共五层。详见第 2 节。

本期讨论产出的设计方向（用户提案）：

1. **砍掉评分**（或仅保留给默认牌阵）——解除最硬的算法约束。
2. **当前"五张时间流"作为默认抽卡方式**，保持原样（含评分 / 动量价值）。
3. **另开一个"牌阵选择"入口**，让其他牌阵走更简单的无评分路径。

## 2. 现状盘点：当前牌阵实现

### 2.1 唯一落地的牌阵（写死）

`packages/core/src/schemas.ts:16-26` 在解读输入契约里内联了一个 `spread` 字段，但用 `z.literal` + `z.tuple` 把 id、名称、**恰好五个中文位置**全部写成常量：

```ts
spread: z.object({
  id: z.literal("five_card_timeline_v1"),
  name: z.literal("五张时间流"),
  positions: z.tuple([
    z.literal("较远背景"), z.literal("早期状态"), z.literal("中间状态"),
    z.literal("近期状态"), z.literal("当前状态"),
  ]),
}),
```

位置标签的真正来源是 `packages/runtime/src/interpretation-input.ts:10` 的 `FIVE_CARD_POSITIONS`（5 元数组），又被 `schemas.ts` 原样抄一遍做校验。数据层（`resources/cards.json`、`data/`）**完全没有**牌阵 / 位置配置。

### 2.2 牌数 `5` 在五层被锁死

| 层 | 位置 | 锁定方式 |
|---|---|---|
| 运行时守卫 | `reading-service.ts:140,175` | `!== 5` 显式校验「请选择恰好五张不同的牌」 |
| 输入契约 | `schemas.ts:32,38,50-56` | `position.max(5)`、`cards.length(5)`、位置必须 `1,2,3,4,5` |
| 输出契约 | `schemas.ts:64-67` | `interpretationSchema.cards.length(5)` |
| 评分公式 | `core/src/scoring.ts` | `if (values.length !== 5)` + 固定 5 项加权 `x5+0.5x4+0.25x3+0.125x2+0.0625x1` |
| 模型提示词 | `desktop/src/main/model.ts`、`mobile/.../model-provider.ts` | system prompt 写明「必须恰好 5 个元素」 |
| UI 文案/计数 | 两端 `App.tsx` 多处 | 「已选 X / 5」、5 个 pip、五张牌文案 |

### 2.3 已具备的可扩展基础（应保留）

- `packages/core/src/deck.ts:27` 的 `randomSelection(random, deckSize=78, count=5)` —— `count` 本就是参数，调用方只是省略了它才默认 5。
- 桌面端 `CardRevealStage.tsx` 用 `useLayout(n, ...)` 按 `cards.length` 自动缩放排布 —— **视觉布局已支持任意张数**。
- `ReadingService.confirmReading` 用 `selected.map(...)` 生成 `revealed`，映射逻辑对张数不敏感。

## 3. 牌阵大全盘点（来自 `docs/塔罗牌阵大全_适用场景与使用方法.txt`）

文档列了 **4 大梯度、16+ 个具体牌阵**，牌数跨度 **1 → 13 张**：

| 梯度 | 牌阵 | 牌数 |
|---|---|---|
| 入门 | 单张牌 / 圣三角 / 三张牌(20变体) / 钻石 / 吉普赛十字 / 二选一 | 1 / 3 / 3 / 4 / 5 / 5 |
| 进阶 | 五芒星(3版) / 六芒星 / 维纳斯之爱 / 要素展开 | 5 / 7 / 8 / 4 |
| 高级 | 凯尔特十字 / 11张凯尔特 / 年度运势 / 关系阵 / 正缘Z字 | 10 / 11 / 12-13 / 11 / 11 |

### 3.1 两个对设计有利的结构性发现

- **"三张牌的 20 种变体"本质是一个 3 张牌阵 + 20 套可切换的位置标签**（问题本质/原因/解决方案、你/对方/关系、选项A/B/如何决定……）。五芒星也有 3 版（周运 / 元素 / 问题分析）。→ 注册表只需支持"同一牌数 + 多套 positions 预设"，核心牌阵可压到 ~12 个。
- **所有牌阵的位置含义文档已用中文写明** → 主要录入工作是机械地把位置标签搬进数据文件。

## 4. 设计方向（用户提案）

- **保留默认**：`five_card_timeline_v1` 作为默认抽卡方式，路径完全不变（含 `scoring.ts` 评分 + 动量/价值叙事）。
- **另开入口**：新增"牌阵选择"界面，用户选完牌阵后再进入抽卡 / 解牌流程；所选牌阵驱动牌数、位置标签、是否评分。
- **砍评分（仅对非默认）**：非默认牌阵不生成 `calculation`（动量/价值数值），解读只输出逐张释义 + 故事线 + 建议。

### 4.1 为什么这个方向可行

上一轮识别的最硬约束是 `scoring.ts` 的固定 5 项加权公式。**砍掉（或仅保留给默认）评分后，该约束消失**。解读生成本质是"逐张描述 + 串故事线"，与张数无关；动量/价值叙事才是 5 张专属。

→ 爆炸半径被控制：当前 5 张路径保持原样；新牌阵走更简单的无评分路径。其余改动全是"把写死的 `5` 换成 `spread.positions.length`"。

## 5. 适配难度评估：改动清单

| 模块 | 改动 | 难度 |
|---|---|---|
| **数据层** | 新增 `Spread` 注册表（`{id,name,category,description,positions[]}`），从文档录入 ~12 个核心牌阵 | 中（录入量大，机械） |
| **schema** | `spread` 改动态（`positions: z.array(z.string())`）；`cards.length(5)` → 超类比对 `spread.positions.length`；`position.max(5)` → 动态；`calculation` 改 `optional` | 小 |
| **runtime** | `createReading` 收 `spreadId`；守卫 `!==5` → `!==spread.positions.length`；`randomSelection` 传 `count=positions.length` | 小 |
| **interpretation-input** | `positionName` 取自 `spread.positions[i]` 而非 `FIVE_CARD_POSITIONS`；非默认跳过 `calculation` | 小 |
| **model prompt** | "必须恰好 5 个元素" → "恰好 N 个（N=牌阵位置数）" | 极小 |
| **UI** | 新增"牌阵选择"入口（两端）；计数/文案动态；`CardRevealStage` 已支持任意张 | **中/大（新界面是主要工作量）** |
| **传统排布** | Z字/十字/圆形等非线性布局 —— 可选打磨，MVP 用网格/列表即可 | 可选 |

**工时估算**：核心数据 + 逻辑改动约 **1–2 天**；UI 新入口（牌阵选择页，两端）约 **2–4 天**；传统非线性排布为可选增强，后续迭代。

## 6. 待决策点（Open Questions）

1. **非默认牌阵的"动量/价值"叙事**（`momentumInterpretation` / `valueInterpretation`）如何处理？
   - 建议：**直接砍**——这两个输出字段改 `optional`，仅默认 5 张填充，其余牌阵只生成逐张释义 + 故事线 + 建议。
2. **三张牌 20 变体**是否作为"一个 3 张牌阵 + 预设位置集下拉"实现，还是拆成 20 个独立牌阵？
3. **牌阵选择入口的位置**：是独立首页 / 启动后的第一屏，还是嵌在现有抽卡流程前一步？两端是否一致？
4. **传统排布保真度**：MVP 是否接受网格/列表式排布，非线性布局（Z/十字/圆）放到二期？
5. **手动选牌 UX**：当前用户从牌带选满 5 张；新牌阵需把可选上限改为 `positions.length`（1 张时几乎是"抽一张"，13 张时需多选交互）。

## 7. 建议的注册表形态（提案）

```ts
type SpreadPosition = { index: number; name: string; hint?: string };

type Spread = {
  id: string;
  name: string;
  category: "入门" | "进阶" | "高级";
  description: string;
  positions: SpreadPosition[];
  // 是否启用评分（默认牌阵为 true，其余 false）
  enableScoring?: boolean;
  // 可选：传统排布坐标，用于未来精修视觉（MVP 可省略，统一网格/列表）
  layout?: "row" | "grid" | "cross" | "z" | "circle";
};

// 例：默认牌阵保持原样
const FIVE_CARD_TIMELINE: Spread = {
  id: "five_card_timeline_v1",
  name: "五张时间流",
  category: "入门",
  description: "时间流视角，照见此刻的路径",
  positions: [
    { index: 1, name: "较远背景" },
    { index: 2, name: "早期状态" },
    { index: 3, name: "中间状态" },
    { index: 4, name: "近期状态" },
    { index: 5, name: "当前状态" },
  ],
  enableScoring: true,
};
```

## 8. 下一步建议（备选路径）

- **路径 A（先打地基）**：仅落地"数据层 `Spread` 注册表 + 默认牌阵不变 + schema/runtime 动态化"，不动 UI。验证默认路径零回归、新牌阵能跑通无评分解牌。
- **路径 B（含 UI）**：在 A 的基础上再做"牌阵选择"入口（两端），形成可演示的多牌阵体验。
- 推荐先走 **路径 A**，把地基与默认路径的回归风险隔离，再单独评估 UI 工作量。
